## Alcance y límites

Revisión local del código Django, requisitos de Python, permisos, archivos y
configuración. Las pruebas usan PostgreSQL 17 y Redis reales, una base temporal
creada por Django y directorios temporales para archivos. Se revisaron metadatos
de la base local; no se accedió al servidor, Nginx ni datos de producción.
No equivale a una certificación de seguridad ni a una auditoría independiente.

No se realizaron pruebas de carga sostenida, pentest del servidor, escaneo de
imágenes del sistema operativo, restauración de respaldos ni validación de TLS
de producción. La prueba de navegador cubrió login y 404 sin iniciar sesión;
los flujos autenticados se verificaron con el cliente de pruebas de Django.

- CSRF y métodos HTTP en altas, ediciones, borrados, folios y archivos.

- Fechas obligatorias al crear y fechas inmutables al editar.

- Errores públicos sin información técnica, incluido DEBUG activado accidentalmente.
- Cuatro creaciones simultáneas del mismo año: ambas tablas completas y secuencias
  sin consumo. Cuatro solicitudes simultáneas de folio para el mismo oficio:
  un único folio y sin avanzar varias veces la secuencia.

## Hallazgos y prioridades

### Alta — actualizar dependencias con avisos de seguridad

| Paquete fijado | Entradas del servicio | Grupos por alias |
| --- | ---: | ---: |
| Django 5.1 | 41 | 24 |
| Pillow 10.4.0 | 66 | 50 |
| sqlparse 0.5.1 | 10 | 6 |
| python-dotenv 1.1.0 | 2 | 1 |

Fuente: consulta de pip-audit al servicio público PyPI. El JSON adjunto conserva
los identificadores y alias; las entradas duplicadas no se cuentan como fallos
distintos en la última columna. No son 119 ataques demostrados contra esta app.
Varios avisos dependen de funciones o formatos no utilizados; por ejemplo, la app
no ofrece un editor de archivos `.env`. Aun así, Django 5.1 original es una base
antigua para mantener un servicio con autenticación y cargas de archivos.

Recomendación: migrar Django a una rama con soporte (por ejemplo, 5.2 LTS con sus
parches vigentes), y revisar versiones corregidas de los otros tres paquetes,
con pruebas de compatibilidad. Generar inventario transitivo y repetir el análisis.
No actualizar todo a ciegas ni ejecutar migraciones sobre producción sin copia.

### Alta — log SQL incluido en Git

`django_db.log` está versionado: 1,915,827 bytes y 26,829 líneas, con operaciones
INSERT/UPDATE. Esto demuestra que se guardó actividad SQL en el repositorio;
no se transcribió su contenido ni se confirmó aquí qué datos personales contiene.
La exclusión `.log` actual no cubre `*.log` y tampoco deja de rastrear archivos
que ya estaban añadidos.

Recomendación: revisar su contenido de forma privada, retirar el archivo del
seguimiento, ignorar `*.log`, definir rotación/retención y limitar permisos.
Valorar limpieza del historial y rotación de secretos solo según lo expuesto;
reescribir Git requiere coordinación. Quitar el archivo actual no borra su historia.
La configuración general también establece logging SQL a DEBUG; su emisión
real depende de que Django active el cursor de depuración.

### Alta condicionada a producción — clave y nombres de servidor

`ivem_digit/settings.py` conserva una SECRET_KEY de respaldo pública en código
y `ALLOWED_HOSTS` con `*`. La configuración local limita hosts, pero la general
no. No se verificó si producción sustituye la clave mediante `IVEM_SECRET_KEY`.

Recomendación: exigir una clave aleatoria externa al repositorio en producción
y permitir únicamente la IP/dominios utilizados. Rotar una clave en uso invalida
sesiones y puede afectar valores firmados: planificarlo. Usar una IP no exige `*`.

### Media/alta según rol — `is_staff` concede autoridad amplia sobre oficios

`documento/access.py` interpreta cualquier `is_staff` como administrador de
ambos departamentos, incluyendo asignación de folios y eliminación lógica.
El administrador dinámico también permite consulta a todo staff. Así, conceder
acceso a Django Admin para gestionar apariencia puede ampliar acceso documental
más allá de los permisos específicos de apariencia.

La nueva pantalla de apariencia funciona sin `is_staff`, lo que permite evitar
esa ampliación al configurar usuarios. Recomendación: definir una matriz explícita
de roles y separar acceso al administrador de operaciones documentales. Este es
un hallazgo de autorización del código, no una escalada externa demostrada.

### Media condicionada a producción — HTTPS, cookies y servidor de aplicación

`check --deploy` local reporta `security.W004`, `W008`, `W009`, `W012`, `W016`:
HSTS, redirección HTTPS, clave de respaldo y cookies de sesión/CSRF sin Secure.
Parte es esperable con HTTP local; no prueba que Nginx de producción esté mal.

Recomendación: verificar TLS y redirección en Nginx, cookies Secure y tratamiento
de cabeceras del proxy. Habilitar HSTS únicamente con HTTPS estable. Compose y
Dockerfile usan `runserver --insecure`: son herramientas de desarrollo, no una
configuración de despliegue de producción. Revisar límites/timeouts de subida.

### Media — privilegios y restricciones de la base

El rol de desarrollo es superusuario, puede crear bases y roles. No se obtuvo el
rol de producción. La automatización anual necesita DDL, pero no privilegios de
superusuario de todo PostgreSQL: revisar un esquema y permisos controlados sin
eliminar la creación automática que requiere el personal.

En las tablas locales 2026, `fecha_oficio`, `activo` y `pendiente` admiten NULL;
los formularios validan fechas, pero escrituras directas podrían omitirlas.
Recomendación: inventariar valores históricos antes de proponer restricciones,
con respaldo y migración compatible; no completar fechas antiguas con valores
inventados ni aplicar NOT NULL sin revisar registros existentes.

### Mejora operativa — recursos externos y recuperación

La interfaz autenticada carga CSS/JS desde CDN y no usa integridad SRI. Revisar
alojamiento local de recursos o integridad y una CSP compatible; probar sin acceso
a Internet desde la red empresarial. Confirmar respaldos conjuntos de PostgreSQL
y MEDIA_ROOT mediante una restauración real sobre otra instancia.

## Interpretación del análisis estático

Las 18 alertas B608 se originan en interpolación de nombres de tablas anuales y
SQL compuesto. Los nombres se restringen a departamentos conocidos y años,
se citan cuando corresponde, y los valores de usuario se pasan como parámetros.
Los casos de inyección añadidos y anteriores pasan; no se confirmó SQL injection.
Mantener esta revisión al modificar consultas, en vez de silenciar B608 globalmente.

La alerta B405 señala `TreeBuilder` de la biblioteca estándar. El parser efectivo
es `defusedxml.DefusedXMLParser` con DTD, entidades y recursos externos prohibidos;
hay límites de profundidad/nodos y pruebas de rechazo. No se confirmó XXE.

## Reproducción

Ejecutar en desarrollo aislado con PostgreSQL y Redis; nunca apuntar las pruebas
a producción ni usar credenciales reales en comandos registrados:

```bash
python manage.py test --noinput
coverage run --branch --source=apariencia,documento,gestion_tables,ivem_digit,login,plantilla \
  --omit='*/tests.py,*/test_*.py,*/migrations/*' manage.py test --noinput
coverage report
python manage.py check --deploy
python manage.py makemigrations --check --dry-run
python -m pip check
pip-audit -r requirements.txt --no-deps --disable-pip
bandit -r apariencia documento gestion_tables ivem_digit login plantilla \
  -x '*tests.py,*test_*.py,*/migrations/*'
```

Herramientas de desarrollo usadas: coverage 7.17.2, pip-audit 2.10.1, Bandit 1.9.4.
Se instalaron en el entorno de trabajo, sin añadirlas a requirements de ejecución.
Los comandos `pip-audit`, Bandit y `check --deploy` pueden terminar con código no
cero por sus hallazgos; eso no significa que la suite de pruebas haya fallado.

Siguiente orden recomendado: dependencias y log versionado; configuración segura
de producción; matriz de permisos; privilegios/consistencia DB y restauración.
Cada cambio funcional o de DB debe entregarse por separado con pruebas y plan de
conservación de la información existente. Esta auditoría no aplica esas correcciones.
